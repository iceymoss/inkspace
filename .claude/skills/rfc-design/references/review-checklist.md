# RFC 评审检查

按实际机制选择检查项；不适用项可以省略。每个问题要落到具体触发条件和可见影响，避免以清单长度衡量设计质量。

## 证据与范围

- 代码事实、参考文档主张、实验结论和提案是否分开？路径/API/版本是否真的核实？
- Implementation notes、ADR、父子 RFC 是否存在明确替代关系？同一不变量是否有权威定义？
- 目标、非目标、前置条件、能力损失和已知破坏是否明示？Greenfield 是否有依据？
- 被拒绝的方案是否实际可行，取舍是否对应当前需求？

## 契约与状态

- 字段范围、必填、空值、未知字段/枚举、损坏和删除是否有确定语义？
- API 身份、资源资格、重复请求、替换/合并、错误响应和部分成功是否完整？
- framing/schema/语义校验分别在哪里？写者和读者是否可能接受不同规则？
- “单一权威”是否限定层级？每个版本/序号的所有者和比较范围是否清楚？
- 每个 ACK、durable、ready、fresh 各证明什么？是否把轮询周期当作生效保证？

## 用反例检查一致性

| 触发场景 | 要检查的后果 |
|---|---|
| 旧触发读取到新 payload | 是否使用正确关联版本，是否允许 coalescing |
| 新记录先于旧记录到达；同键在同批次重复 | 胜出规则、批内状态和原子写是否正确 |
| 持久化已成功，ACK 或活动完成通知丢失 | 重试是否重复副作用；失败是否被误判为未写入 |
| DB 已提交，下游未确认启动，随后又有更新 | 恢复是否会覆盖后来状态；是否错误补偿 |
| filter/index 先于记录，记录先于依赖到达 | 是否安全不可用；是否会永久缓存缺失 |
| 新空值/reset 与旧配置逆序到达 | 是否能清掉旧状态；是否因“空”被跳过发布 |
| 旧成功、旧错误或旧 absent 晚于新状态返回 | 是否能阻止覆盖，是否保留必要重试 |
| 出错后没有新写入/通知 | 恢复是否仍有触发机制 |
| 故障恢复后得到相同有效序号 | 是否能重新激活，是否错误地保持 degraded |
| 存储故障期间重启 | 与已启动后故障相比能力是否不同 |

## 资源、运维与验证

- 总 deadline 是否包括排队与所有候选/依赖读取？各层 timeout、backoff 和尝试次数是否算得通？
- 是否限制并发、缓存容量、后台每轮工作和退出时间？I/O 是否持有 serving 锁或阻塞运行时线程？
- 缓存的淘汰、预热范围与不完整性是否说明？是否误称副本或离线启动来源？
- 健康与新鲜度是否分开？指标是否能区分失败、合法默认、尚未初始化和恢复成功？
- 实验性机制是否有评估方式和退出标准？数值是否有来源或明确标为初始默认？
- 实施表是否包含必要的路由/worker 注册、配置、资源生命周期、mock 和调用者更新？
- 验证场景是否从不变量推导？mock/POC 是否被错误当作真实行为已验证？

## 评审输出

按重要性输出：`位置/契约 → 触发条件 → 影响 → 建议修正 → 验证方法`。

把会改变正确性、对外行为或实施范围的问题与可选编辑建议分开。缺少依据时写为待确认问题，不将推测作为已证实缺陷。只在必要时建议新机制，优先在现有范围内消除歧义。
