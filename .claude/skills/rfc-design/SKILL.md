# 工程 RFC 设计

把技术需求转成可评审、可实施、可验证的设计。核心交付是让各组件实现者对同一边界得出一致行为，尤其覆盖并发、部分成功和恢复过程。

本 skill 从三份证书分发与动态路由 RFC 提炼。具体来源、修订关系和反例见 [references/design-patterns.md](references/design-patterns.md)，需要借鉴原文设计时再读。它们的技术栈和局部策略不是新项目的默认要求。

## 任务入口

- **新建 RFC**：先查明背景和关键约束，再确定方案与契约；按需改写 [assets/rfc-template.md](assets/rfc-template.md)，删去不适用章节。
- **完善 RFC**：保持已确认范围与决策，补足会影响实现的歧义；涉及实质性方案变化时解释原因。
- **评审 RFC**：阅读 [references/review-checklist.md](references/review-checklist.md)，只报告有具体触发条件、影响与修正建议的问题。未发现问题时不强凑清单。

沿用用户要求的语言、仓库规范和文档编号。未指定时用用户当前语言，保留 API、类型、字段与术语的原始标识符。

## 1. 事实取证：先确认系统现在能做什么

从需求、现有 RFC、代码、配置、依赖版本和实验中建立事实表：`主题 | 已知事实 | 证据位置 | 设计影响`。

区分已有行为、实测结论、待验证假设与本次提案。能访问仓库时核对入口、实际调用链和版本对应的 API；只有文档时，写“参考文档描述”，不要声称检查过代码。

对相互冲突的材料检查状态、更新时间、Implementation notes、ADR 和明确的 supersedes/deviation 关系。显式修订优先于被替代段落；不能判断时列出冲突，不用日期单独推断所有权威关系。

实验需交代环境、数据规模、测量对象与未测范围。初始默认值、局部实验延迟与生产保证分别表述。只有决策确实依赖未知机制时才建议 POC，并说明什么结果会改变选择。

## 2. 范围界定：目标、代价和责任归属

明确当前问题、目标行为、非目标、前置条件和可接受限制。说明受影响组件、每个组件的责任，以及不在本次修改范围内的依赖。

分别界定业务写入权威、下发投影、运行时读取来源与本地缓存。使用“唯一事实来源”时写清针对哪一层，避免把 OLTP、分发数据库与缓存都称为全局权威。

列出少量实际可行的备选方案，按当前约束比较复杂度、资源成本、故障能力和失去的能力。选最小足够方案，避免为想象中的需求引入框架、独立持久化或额外配置。

Greenfield、已有部署、是否允许破坏兼容必须来自证据。存在迁移需求时设计迁移；没有时不机械添加双写、回填或回滚系统。

## 3. 契约设计：沿数据流定义边界

先画出真实组件间的数据流，再按边界或组件展开，不限定所有设计采用相同分层。

对相关边界写清输入、输出、所有者、校验和可见行为：

- **数据/存储**：键与隔离范围、字段类型/范围、必填和默认、空值/缺失/删除/损坏的差别；二进制格式还需字节宽度、端序、长度、校验覆盖、非法输入与可核算示例。
- **API**：方法/路径、鉴权与资源资格、请求/响应、错误类别、替换或合并、重复请求和并发语义；区分业务错误与框架提取错误。
- **工作流/队列**：触发方式、实例身份及复用规则、活动职责、持久化确认点、重试分类、结束条件。
- **运行时读取**：选择身份的可信来源、查找优先级、缓存命中/缺失、依赖未到达、刷新与生效粒度。

把 framing、schema、语义和运行时编译校验分开，标明各自执行层。多组件需相同语义时优先共享模型/校验器，不能共享时定义一致性用例。不要让各实现自行猜测同一规则。

解释未知字段和未知枚举分别如何处理、破坏性格式变更如何升级、生产者和消费者的部署先后顺序。只固定确有证据要求的库版本。

## 4. 一致性推理：版本、原子性和确认点

枚举各类版本/序号：谁分配、何时增加、作用于什么键或对象、能在哪个生命周期内比较。业务 revision、存储 seq、manifest generation 和进程内刷新 generation 不互相冒充。

版本与 payload 的关联规则应按业务选择，不能照搬案例：最新快照投影通常需要同一次一致读取得到 payload 与 revision；事件型发布则需明确事件版本与事件内容的绑定。若允许相同版本产生不同快照，写出适用对象、胜出规则及仍能成立的不变量。

明确每个原子性边界：数据库行更新、版本递增、单条队列操作、批次写入、运行时指针替换。写入顺序不自动保证多键原子可见；依赖顺序发布仍需读者处理依赖缺失。

对每个 ACK 定义“已证明什么”：数据库提交、工作流启动、buffer durable、ingest durable、reader 可见、运行时激活。只列真实存在的阶段，不把前一阶段的成功表述成端到端生效。

为重复、乱序、同版本冲突、超时后已成功、持久化后完成通知丢失设计规则。给出关键交错案例证明不变量；不要用“最终一致”替代分析，也不要把可重试启动写成 exactly-once。

## 5. 故障恢复：写明状态如何变化

用 `触发/观察 | 对外行为 | 重试/恢复 | 退出条件` 描述启动未就绪、正常、合法空值、权威缺失、数据损坏、读取失败、过期结果和恢复。

每项降级策略都须按领域选择：默认配置、保留最后有效值、拒绝服务或限定功能均可能合理。不要把案例中的路由失败切默认推广为证书、权限或所有配置的统一策略。

刷新设计需覆盖候选构建、完整校验、原子激活、旧异步结果失效和待重试义务。考虑旧成功、旧失败、缺失和删除结果如何与新状态竞态；只有行序号未必能排序没有序号的观察结果。

检查两类容易遗漏的恢复：没有新写入/通知时能否重试；失败后重新读到同一有效序号时能否恢复。若策略依赖定时重试、请求重试或人工操作，写明触发者和停止条件。

数据库提交后触发下游失败属于部分成功：说明已提交状态、客户端能安全重复什么、是否接受投递空窗。不要擅自补偿回滚，也不要未经需求就引入 outbox/reconciliation。

分别分析启动、运行中故障、故障中重启和恢复后的能力；缓存可维持部分服务不等于它能离线启动或充当完整副本。

## 6. 资源与运维：预算可计算，状态可观测

只对实际相关机制定义总 deadline、各层超时、退避与总尝试次数，验证嵌套重试是否能在外层预算内完成。区分最大尝试次数与额外重试次数。

涉及后台刷新或冷读时说明并发限制、去重、排队是否计入 deadline、每轮工作预算、缓存容量/淘汰和资源生命周期。说明谁创建/关闭资源、是否跨 runtime 重建存活、如何有界退出。

把 serving、readiness、freshness、durability 与 warming complete 分开。轮询周期、最大主动延迟和本地实验耗时都不能直接充当端到端延迟上界。

为关键状态和恢复条件配指标/日志，区分成功空闲、失败尝试与最后成功时间。标签维度保持有界；域名、路径、工作流 ID 和精确版本放日志或状态页。实验性机制如要长期保留，定义负责人、评估窗口、指标与退出标准。

## 7. 实施拆分：让变更可以交给工程师

用 `组件/文件或模块 | 必要变更 | 依赖/前置条件 | 验收证据` 给出实施边界，文件路径仅在已核实或明确标为建议时使用。

把共享契约、生产者、传输/ingest、消费者的依赖顺序写清；指出注册入口、配置与环境覆盖、资源注入、mock/harness 和文档的必要更新。阶段间如暂时破坏调用者，明确具体影响及由哪个后续阶段修复。

保持范围聚焦，不把邻近重构混入本次设计。跨 RFC 的不变量指定一个权威位置，其余引用，避免多个完整定义逐渐漂移。

## 8. 行为验证与交付

从不变量和状态转换推导验证矩阵：`场景/交错 | 输入或故障 | 预期可见行为 | 验证层级`。重点覆盖被拒绝请求无副作用、重复/乱序、部分成功、依赖缺失、陈旧结果、故障恢复和适用的兼容边界。

编解码示例可作为 golden tests；真实行为依赖 TLS、对象存储或数据库时，标明相应集成验证，不能让只验证 mock 水位或复制实现的测试代替真实调用链。设计阶段给出验证计划，不声称测试已运行。

交付前按 [references/review-checklist.md](references/review-checklist.md) 做一致性检查。区分已决定、需验证和待决问题；待决项写清阻塞哪项决定、需要何种证据或谁来确认。信息不足仍可交付带明确假设的草案，不能编造实测数字、代码事实或已完成状态。
