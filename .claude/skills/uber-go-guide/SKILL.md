# Uber Go 编码规范

将 Uber Go Style Guide 中文版转化为实现与审查的操作清单。只应用与当前改动有关的规则，不借规范检查扩大改动范围。

## 1. 确定范围与项目约束

- 写代码：确定要修改的包、行为和兼容性要求。
- 重构：确认需要保持的公共 API、序列化结果和错误契约。
- 审查：使用用户给定的文件或 diff；范围不明确时先确认。审查只输出发现，用户要求修复时才修改代码。
- 先读根目录 `CLAUDE.md`、目标目录适用的 `.claude/rules/`、`go.mod` 和相邻实现。**项目明确约定优先于本 skill 的风格偏好**，正确性问题仍需指出。

完成条件：能明确列出本次范围、适用的 Go 版本及与本指南冲突的项目约定。

## 2. 按改动加载规则

| 改动涉及 | 必须查阅 |
| --- | --- |
| error、接口/接收器、集合边界、锁、channel、goroutine、初始化或退出、时间/序列化 | [正确性与生命周期](references/correctness.md) 中的对应章节 |
| 命名、import、声明/初始化、控制流、测试、构造函数选项、性能优化 | [风格、测试与模式](references/style-and-patterns.md) 中的对应章节 |
| 规则出处、与原文差异、严格按 Uber 原文审查、更新 skill | [来源与适配说明](SOURCES.md) |

以下项目适配始终生效：

- 数据库访问、分层和统一响应遵循项目约定；不能因指南偏好依赖注入而重构现有数据库单例。
- 当前包未采用未导出顶层符号的 `_` 前缀时保持一致；只有明确要求采用纯 Uber 风格时才引入。
- 使用当前 Go 版本支持的标准库类型化 `sync/atomic`；已有 Uber atomic 用法可保留，不为遵循指南新增依赖。
- 遵守 API 的 `null` / `[]` / `{}` 契约，不将 nil 集合偏好变成响应格式变更。
- 框架约定的模型嵌入按项目规则保留，不机械套用公共结构体嵌入的限制。
- 日志归属结合调用链和项目规则判断；有意的跨边界观测不直接等同于错误的重复日志。

完成条件：每个改动点都已归入适用章节；未涉及的规则无需展开。

## 3. 实现或审查

按风险顺序检查：

1. **正确性**：错误是否可匹配、类型断言是否安全、集合是否泄露内部状态、零值是否可用、时间单位和序列化契约是否明确。
2. **生命周期**：资源是否在所有返回路径释放；共享状态是否一致同步；goroutine 是否能停止并被等待；阻塞发送/接收是否有退出路径。
3. **可维护性**：公共 API 是否暴露实现细节；命名和声明是否与包内一致；正常路径是否被多层分支淹没。
4. **验证与性能**：测试是否覆盖行为、边界与失败；性能结论是否有 benchmark 或 profile 支撑。

写代码时把规则落实在本次变更中；审查时为每条发现记录：`路径:行号 → 规则 → 具体影响 → 最小建议`。区分：

- **正确性问题**：有可解释的失败路径、竞态、泄漏或兼容性破坏。
- **规范偏差**：违反明确适用的项目规则或本指南规则。
- **可选建议**：上下文相关的风格和性能偏好，不能冒充 bug 或阻断项。

完成条件：所有改动点均检查过适用规则；发现有代码证据与具体后果，项目例外已排除。

## 4. 验证与交付

有 Go 代码修改时：

- 仅格式化修改的 Go 文件；项目配置了 `goimports` 时沿用该配置，否则用 `gofmt`。
- 先跑受影响包的测试，再按影响范围运行 `go test ./...` 和 `go vet ./...`。
- 涉及并发状态或生命周期时，在环境支持的情况下对受影响包运行 `go test -race`。
- 性能优化在相同环境比较前后 benchmark，并关注 `-benchmem`；原指南的历史数字不作为当前收益保证。
- 沿用仓库已有 lint 配置；不擅自安装工具、引入依赖或新建 lint 配置。

纯审查可使用只读检查和针对性测试，不执行写入式格式化。仅更新文档时检查 frontmatter、本地链接和来源即可。

交付时说明改动或按风险排序的发现、适用的项目例外、实际执行的验证及未验证原因。无发现时明确说明覆盖范围，不能把未执行的测试写成通过。
