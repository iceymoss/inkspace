# Go 标准注释规范

为当前任务范围内的 Go 代码添加准确、必要、符合 Go 官方惯例的注释。

注释应帮助维护者理解设计意图、调用契约、关键约束和非直观行为。对于复杂结构体、重要方法和关键逻辑，应主动补充合适的说明。

## 工作原则

1. 先阅读实现、相关调用方和测试，再编写注释。
2. 优先遵守项目已有的注释语言和术语约定；没有明确约定时，注释默认使用英文，保留 Go 标识符和必要的英文术语。
3. 注释必须与实际行为一致，不推测或编造设计动机、并发保证、错误语义和性能指标。
4. 单纯补充注释时，不修改实现、签名、标识符、结构体标签和工具指令。
5. 普通功能修改只处理相关代码；用户明确要求全包或全项目补充注释时，再按指定范围检查。
6. 修改代码时同步更新失效的注释，避免注释与实现矛盾。

## Go 文档注释格式

### 基本格式

- 普通注释优先使用 `//`。
- 文档注释放在对应声明正上方，中间不留空行。
- 文档注释使用完整句子，并以适当的标点结束。
- 类型、接口、函数和方法的文档注释首句，以对应声明的准确名称开头。
- 方法注释以方法名开头，不以接收者变量名开头。
- 首段提供简洁摘要，后续段落补充行为约定和设计背景。
- 段落之间使用单独的 `//` 行。
- 不必为了统一样式，批量改写已有合法的 `/* ... */` 注释。

示例：

```go
// Config 保存服务启动所需的配置。
type Config struct {
    // Timeout 是单次请求的超时时间；零值表示不设置超时。
    Timeout time.Duration
}
```

### 包注释

- 包注释以 `Package <包名>` 开头，说明包的用途及主要使用约束。
- 通常放在一个文件的 `package` 声明之前。
- 较长的包文档可以放在 `doc.go` 中。
- 不在同一个包的每个文件中重复包注释。
- `main` 包可以直接描述程序用途。

示例：

```go
// Package scheduler 提供按优先级执行后台任务的调度器。
//
// 调度器启动后可以并发提交任务；关闭后不再接受新任务。
package scheduler
```

以上行为描述仅适用于实现确实满足这些约定的情况。

### 文档排版

- 使用 Go 文档支持的格式。
- Go 1.19 及以上可以使用 `// # 标题`，标题前后留空注释行。
- 使用 `[Type]`、`[Type.Method]`、`[io.Reader]` 等文档链接时，确保对应符号真实存在且可以解析。
- 文档注释中的代码示例使用缩进代码块。
- 不将 Markdown 的三反引号围栏、表格或 `@param`、`@return`、`@throws` 当作 Go 标准文档语法。
- 旧版本项目使用对应工具链支持的格式。

### 弃用说明和工具指令

- 弃用说明使用独立段落，以准确的 `Deprecated:` 开头。
- 有替代方案时，说明应使用的 API。
- 不自行将正常使用的 API 标记为弃用。
- 保留已有 Swagger 等工具要求的注解。
- 保持 `//go:build`、`//go:generate`、`//go:embed`、`//go:noinline`、`//line`、`//nolint` 等指令的位置、拼写、参数及必要空行。

示例：

```go
// Parse 解析 src 并返回配置。
//
// Deprecated: 请使用 [ParseConfig]，以便显式指定解析选项。
```

这些属于 Go 文档惯例及本 skill 的质量要求，不应描述成编译器强制要求所有声明都必须有注释。

## 注释覆盖范围

### 导出声明

为当前任务涉及的导出类型、接口、函数、方法、常量和变量提供适合该声明的文档注释。

- 简单的分组常量可以使用清晰的组注释。
- 含义独立或不明显的成员应分别说明。
- 不仅重复声明名称，还应补充使用者需要知道的信息。

### 复杂结构体

重要或复杂的结构体应说明：

- 职责、用途和抽象边界。
- 核心状态及必须维持的不变量。
- 重要字段之间的关联和约束。
- 零值是否可用，是否需要通过构造函数初始化。
- 使用后是否可以复制。
- 是否允许并发调用，哪些状态由锁保护。
- 持有资源的生命周期，以及关闭或释放责任。

字段含义不直观时，说明：

- 用途、单位、取值范围及缺省值。
- `nil`、空值和零值的区别。
- 数据所有权、共享关系和可变性。
- 锁保护关系及访问要求。

根据实际复杂度选择必要内容，不要机械套用所有项目。命名已经充分表达含义的简单私有字段，可以不添加重复说明。

### 接口

接口注释应说明实现者和调用者共同遵守的行为契约。

必要时说明：

- 方法的调用顺序。
- 并发使用约定。
- 阻塞、取消和关闭行为。
- 错误及部分结果的语义。
- 输入输出数据的所有权。

不要把某个实现的内部细节写成整个接口的通用要求。

### 函数和方法

重要方法、复杂函数及非直观的未导出辅助函数，应说明：

- 实际用途及可观察效果。
- 调用前置条件。
- 重要参数的含义及约束。
- 返回值及特殊值的含义。
- 主要错误条件。
- 失败时是否已经产生部分结果或副作用。
- 必要的生命周期和并发约定。

根据实际行为补充：

- `nil`、空集合、零值和非法范围的处理。
- 重复调用、幂等性及调用顺序要求。
- 是否阻塞，以及何时返回。
- `context.Context` 的取消和超时如何影响操作。
- 调用方是否需要关闭或释放返回的资源。
- 实现支持的 `errors.Is`、`errors.As` 判断方式。
- 调用方需要知道的、有意触发的 panic 条件。

不要因为函数接收 `context.Context`，就默认承诺可以及时取消。
不要无依据地承诺“并发安全”“不会 panic”或“不会阻塞”。

简单且命名清楚的未导出辅助函数，可以省略没有额外信息的注释。不要给每个方法套用固定的参数和返回值模板。

### 关键逻辑

在以下逻辑存在理解成本时，添加贴近代码的块级说明：

- 复杂条件分支和循环。
- 算法的关键阶段。
- 状态转换及其合法条件。
- 缓存失效、淘汰和一致性策略。
- 事务边界、重试和补偿逻辑。
- 锁顺序、channel 关闭责任和阻塞条件。
- 边界计算、区间开闭、单位换算和溢出防护。
- 哨兵值、特殊兼容处理和非直观的性能优化。

重点解释：

- 为什么这样处理。
- 依赖哪些前提。
- 必须保持什么约束。
- 哪些边界容易导致错误。

不要逐行复述赋值、循环或常见的错误返回。

## 示例

以下示例展示注释格式和说明重点。将其中的行为描述用于其他代码前，必须核实对应实现。

```go
// Cache 保存具有过期时间的字符串条目，允许多个 goroutine 并发调用其方法。
// Cache 的零值可直接使用，首次使用后不得复制。
// 过期条目在读取时被视为未命中，但不会立即从内存中移除。
type Cache struct {
    // mu 保护 items 及其中的条目。
    mu sync.RWMutex

    // items 按键保存条目；nil 表示尚未写入。
    // 首次写入时，需要在持有 mu 写锁期间初始化。
    items map[string]entry
}

// entry 保存单条缓存记录，由所属 Cache 的 mu 保护。
type entry struct {
    value string

    // expiresAt 是过期时刻；零值表示永不过期。
    expiresAt time.Time
}

// Get 返回 key 对应的未过期值及命中状态。
// 键不存在或条目已过期时，返回空字符串和 false。
func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()

    e, ok := c.items[key]
    if !ok {
        return "", false
    }

    // 过期时刻本身也视为过期；零值单独表示永不过期。
    if !e.expiresAt.IsZero() && !time.Now().Before(e.expiresAt) {
        return "", false
    }

    return e.value, true
}
```

## 检查与交付

完成后检查：

1. 当前范围内的复杂结构体、重要方法和关键逻辑是否已有必要说明。
2. 文档注释是否紧邻声明，首句是否以正确名称开头。
3. 注释是否与实现、调用方及测试一致。
4. 并发、错误、取消、零值和资源生命周期的描述是否有依据。
5. 是否存在逐行翻译代码、重复命名或已经失效的注释。
6. 文档链接、弃用说明及工具指令是否准确。

修改 Go 文件后，使用仓库约定的格式化方式；通常对修改过的文件运行 `gofmt`，并审查差异。

涉及较长文档、标题或链接时，使用 `go doc` 检查实际展示效果。

纯注释修改通常不需要新增测试；遵守仓库已有的检查要求。交付时简述补充了哪些说明、执行了哪些检查，以及仍无法确认的内容，不声称执行了未运行的命令。
